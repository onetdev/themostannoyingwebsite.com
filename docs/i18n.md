# Internationalization (i18n)

The project supports UI and content translation.

Two different translation systems exist:

- UI translations
- content translations

## UI Translation

UI translation is implemented using **next-intl**.

All user-facing text must be translated. Hardcoded UI text should be avoided.

Translation files are located in:

```
apps/web/src/i18n/messages
```

or within feature modules:

```
src/features/*/i18n
```

## Translation File Patterns

Only English is bundled, one file per feature.

Simple and complex UI translations alike use a single file per feature:
`src/features/*/i18n/en.ts`, plus the global `src/i18n/messages/en/` bundle
(`index.ts`, `common.ts`, `metadata.ts`).

Non-English UI translations are served by the headless Content API and merged
over the English bundle at runtime.

### Static rendering

The root layout lives at `src/app/[locale]/layout.tsx` and the `[locale]`
segment is read through **`next/root-params`** in
`src/core/i18n/request.ts`. Because the locale comes from the root parameter
instead of request headers, pages no longer need `setRequestLocale` (deprecated
in the installed next-intl — check `node_modules/next-intl`) and stay statically
renderable with `generateStaticParams`.

`app/layout.tsx` must **not** exist: a pass-through root layout would move the
root boundary above `[locale]`, leaving `next/root-params` unable to see the
segment. Unmatched URLs are handled by `app/global-not-found.tsx`
(`experimental.globalNotFound`).

### Language suggestion copy

The language-suggestion toast speaks in the *suggested* language. Its copy is
fetched per locale from the Content API
(`translations/{lang}?namespace=languageDetector`) on the server, keyed by
locale, and provided to the client through `LanguageDetectorMessagesProvider`.
The bundled English `languageDetector` namespace is the reference and fallback.

## Variant Pools

Large structured datasets (fake names, comment templates, testimonials, quiz
questions, social-proof data, etc.) are **not** bundled and do not live in
translation files. They are served exclusively by the Content API:

- Services fetch them with `getVariantPool` (`client.variants.getByType`).
- Client components read them with `useVariantPool`, from a React Query cache
  that is prefetched on the server (per route) and hydrated into the payload, so
  no browser runtime Content API calls are made.

See `adr/0025-api-only-variant-pools-ssr-hydration.md`.

## Content Translation

Content such as articles and media metadata is handled by the **content-sdk** package connecting to the headless Content API.

Location:

```
packages/content-sdk
```

This package communicates with the headless Content API at runtime and during static build generation.

More details are available in:

```
packages/content-sdk/README.md
```

## Locale vs Language

The project distinguishes between:

- **language** → translation selection (`en`, `hu`)
- **locale** → formatting rules (`en-US`, `hu-HU`)

Translations typically operate on the **language level**, while formatting uses the **locale**.

Example:

```
language: hu
locale: hu-HU
```
